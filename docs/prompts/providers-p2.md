# Providers — Phase P2: settings store, secrets, secure settings API (no GUI yet)
Rules: do NOT touch config/selfieModeration.json or server/personality.js. Do NOT commit; list changed files. Keep all tests passing (report counts). No new npm dependencies. Hermetic tests (temp dirs, fake servers; the existing test setup guard applies). No secrets or machine paths in logs/reports. npm run check:privacy must pass. Stop after P2.
1. Settings model. Non-secret user settings live in <local>/settings.json: profiles (id, adapter, baseUrl, flags, header NAMES), slots (profile, model, params, timeouts), ui prefs (language id|en, default id). Strict allow-list schema: unknown fields rejected; safety/moderation/persona settings are NOT part of the schema and unreachable through any API. Layering: committed templates < providers.config.local.json (dev override) < settings.json (GUI-written) < env vars (secrets only). A per-field "source" report (default/dev-file/settings/env) for the future GUI. Atomic writes (temp+rename), a version number for optimistic concurrency, size limits, corrupt-file recovery with a backup.
2. SecretStore interface {get,set,delete,has,backendName} with backends: (a) env (read-only, wins when the variable is set); (b) windows-dpapi: encrypts per-user with DPAPI through a PowerShell child process (ProtectedData, CurrentUser scope), command runner injectable for tests, ciphertext in <local>/secrets.dat; (c) plaintext-file fallback ONLY when the user explicitly opts in, with a persistent warning in status. Backend selection reported in status. Secrets also cover extra header VALUES and bodyExtras that look like credentials. Key rule: a secret is bound to its profile's baseUrl origin; changing baseUrl of a profile that has a stored secret requires the new secret in the same request or an explicit confirmation that deletes the old one. Never log, return, export or snapshot secret values (status may expose only has:true and the last 4 chars when the key is >= 20 chars).
3. Settings API on the backend (/api/settings/*): GET effective settings (masked) + sources; PUT profile; PUT slot; DELETE profile (refuse when a slot uses it unless force); PUT/DELETE secret (write-only); POST test (shared testSlot with ephemeral overrides, rate limited and size/timeout bounded); GET status (getSlotStatus for all slots, warnings: plaintext http, plaintext secrets, missing slots, firstRun flag); POST export (no secrets, no local paths) and POST import (validated against the schema, never imports secrets). Security: loopback peer only (also through the Vite/Electron proxies: trust forwarded headers only from loopback, like the image routes); Host allow-list (DNS-rebinding defence); mutating and secret endpoints require same-origin (Origin/Sec-Fetch-Site) AND a per-session token in a custom header; no CORS headers; the token is obtained from a same-origin bootstrap endpoint; Cache-Control: no-store; baseUrl validated by the existing validator; no redirects. Mobile/LAN clients cannot reach these endpoints.
4. Hot reload: after a successful change call registry.reload(); in-flight requests keep their provider (already specified); broadcast {type:'settings_changed', slots:[...]} over the existing WS with no values.
5. Migration (explicit only): GET /api/settings/legacy reports which known env vars and local config entries exist (names only); POST /api/settings/legacy/import copies NON-secret choices into settings.json on request; env keys keep working in place and are never copied into the store automatically.
