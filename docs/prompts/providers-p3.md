A. Backend follow-ups (small)
1. Stale lock recovery: a settings lock is stale when its owner pid is not alive AND age > configurable threshold; recover automatically, otherwise return a clear actionable error code (never a silent failure).
2. Probe deadline: POST /api/settings/test accepts timeoutMs (default 20000, max 60000, bounded) instead of the fixed 5 s; report progress phases (connecting, first byte, done).
3. POST models-list helper: asks a profile (stored secret or one-time key in the request body, never persisted unless saved) for GET {baseUrl}/models and returns NAMES only (bounded count and length, sanitized); failure = empty list with a reason code; same security rules and rate limits as the rest of the API.
4. `npm run settings:doctor`: self-test of the secret backend with a random dummy value (store, read back, delete; never touches real keys), reports backend name, file locations, permissions/ACL notes, stale locks, settings version and corrupt-backup presence. Also expose it to the GUI Diagnostics tab via the API.
B. GUI (page #settings of the existing frontend; thin rendering, logic in pure testable modules)
1. Entry points: gear button in the desktop debug panel; Electron tray item "Settings…" opening a window that loads the same frontend origin at #settings (contextIsolation stays on). Non-loopback/mobile clients must NOT show the entry; they see a short "open settings on the host computer" notice.
2. Tabs: Connections (providers + slots), Status, Privacy, Diagnostics, Language. Wizard state survives reloads.

API key field is write-only, type=password, autocomplete=off, cleared after save, never echoed; show only has/last4 from the API. Changing a baseUrl of a profile with a stored key forces re-entering the key or an explicit "delete the stored key" confirmation (mirrors the backend rule).
